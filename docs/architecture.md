# Архитектура Timdoc

## Измеримый результат

Для каждой позиции техники из текстового PDF-акта приложение создаёт три отдельных
редактируемых DOCX: талон владельца, Форму 4 и Форму 11. Для тестового акта с шестью
заводскими номерами результатом являются 18 файлов и один ZIP-архив.

## Ограничения первой версии

- Windows 10/11, Microsoft Word установлен.
- Только PDF с текстовым слоем, без OCR.
- Работа полностью локальная.
- Исходные шаблоны не изменяются.
- Старые DOC преобразуются в DOCX через Word при импорте: на Windows через COM,
  на macOS (для разработки и демонстрации) через AppleScript.
- Бинарные шаблоны и пользовательская база не хранятся в Git.

## Модули и тестовые швы

- `ActParser.parse(path) -> ActData`: PDF в проверяемые реквизиты и позиции техники.
- `CustomerStore`: сохранение хозяйств и настроек исполнителя в SQLite.
- `DocumentGenerator.generate(request) -> GenerationResult`: три DOCX на позицию и ZIP.
- `AppFacade`: небольшой интерфейс, который использует локальный SPA.

Сложность форматов и хранения закрыта реализациями модулей. Интерфейс не знает о PDF,
OOXML, SQLite или автоматизации Word.


## Как заполняются шаблоны

Подготовка шаблонов (`TemplatePreparer`) выполняется один раз для папки исходников и
повторяется только когда меняется содержимое файлов (SHA-256 в `templates.json`).

- Талон: значения подставляются в ячейки таблицы реквизитов, заводской номер разбивается
  по 14 клеткам, подпись сервисного центра повторяет заполненный образец:
  21 подчёркивание, фамилия размером основного текста с линией под ней, `М.П.`.
  Хвостовые пустые абзацы ячейки убираются, чтобы обе печатные копии остались на одной
  странице. Внешние колонки талона выравниваются по ширине (в исходнике правая уже),
  иначе длинные значения переносятся только в одной копии. Новые ран-ы берут шрифт со
  знака абзаца ячейки (Tahoma), иначе Word подставит Calibri.
  «Дата постановки на гарантийный учёт» не заполняется.
- Формы 4 и 11: поле определяется по подписи под линией (`(марка Продукции)`, `(номер)`
  и т. д.). Заменяется только блок подчёркиваний в абзаце над подписью; текст-префикс
  (`провел работы по обслуживанию`), табуляции и линии для стороны потребителя
  сохраняются. Блок подчёркиваний превращается в три рана:
  `{{ поле | blank_left(N, S, B) }}{{ поле }}{{ поле | blank_right(N, S, B) }}`, где `N`
  — число подчёркиваний линии, `S` — её кегль в полупунктах, `B` — жирность (из рана
  или стиля абзаца через `styles.xml`). Добивка слева и справа остаётся в стиле линии,
  значение набирается 11 pt обычным с подчёркиванием. Фильтры (`generator.py`)
  считают добивку по метрикам Tahoma и Tahoma Bold (`metrics.py`, таблицы
  `tahoma_widths.json` и `tahoma_bold_widths.json`, извлечённые скриптом
  `scripts/extract_font_widths.py`), так что линия сохраняет печатную длину и никогда не
  становится длиннее исходной: иначе табуляции блока подписей уезжают и правая колонка
  переносится.
  Пустое значение оставляет линию для ручного заполнения. «Дата составления» и
  контактное лицо потребителя не заполняются: в подписанных образцах их вписывают от
  руки.

Преобразование DOC выбирается по платформе (`default_converter`): `WindowsWordConverter`
(COM), `MacWordConverter` (AppleScript), иначе понятная ошибка. Word для Mac работает в
App Sandbox и спрашивает доступ к каждому файлу вне своих папок, поэтому файлы на время
преобразования копируются в его групповой контейнер
`~/Library/Group Containers/UBF8T346G9.Office/Timdoc` и удаляются после.
